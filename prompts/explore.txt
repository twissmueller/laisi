## The 7 Quality Gates

### 1. ATOMIC
The requirement describes exactly ONE demand.
Detection rule: Does the text contain "and", "as well as", "furthermore", "additionally"
connecting two different functionalities? → Split them.

### 2. UNAMBIGUOUS
The requirement is free of vague, subjective, or ambiguous terms.

Forbidden terms (BLACKLIST):
- Performance: fast, quick, performant, responsive, efficient, timely,
  near real-time, lightweight
- Quality: simple, intuitive, user-friendly, robust,
  reliable, secure, appropriate, adequate
- Quantity: some, several, many, few, sufficient, minimal, enough
- Open ends: etc., and/or, but not limited to, as needed,
  if required, where possible, if applicable
- Time: soon, shortly, as soon as possible, in due time

When you find one of these terms in the issue:
1. Flag it under <flagged_terms>
2. Suggest a concrete, measurable replacement
3. If you cannot determine the replacement yourself,
   ask a follow-up question

### 3. TESTABLE
The requirement can be translated into a concrete acceptance criterion.
Each criterion must be formulated so that a test (manual or
automated) yields a clear PASS or FAIL result.

Bad: "PDF should look correct"
Good: "PDF contains company logo at top left, invoice number in
     font size 14pt, all line items as a table with columns:
     Description, Quantity, Unit Price, Total Price"

### 4. COMPLETE
All relevant aspects are covered:
- Normal case (Happy Path)
- Error cases (What if input is empty? Invalid? Too large?)
- Boundary values (Minimum, Maximum, empty list, one element, many)
- Permissions (Who is allowed? What if not authorized?)
- Side effects (What else is affected? Logs? Notifications?)

If aspects are missing and you CANNOT reliably derive them from context
→ Ask a follow-up question. Do NOT guess.

### 5. CONSISTENT
The requirement does not contradict any other requirement in this issue.
Also check for implicit contradictions, e.g.:
- REQ-A says "all users can do X" and REQ-B says "only admins can do X"
- REQ-A says "synchronous" and REQ-B implies bulk processing

### 6. IMPLEMENTATION_FREE
The requirement describes WHAT, not HOW.

Detection rule: Are specific technologies, libraries, database
schemas, API endpoints, or architecture decisions mentioned?
→ Remove the implementation part, keep the requirement.

Bad: "Use Redis as cache for the PDFs"
Good: "Repeated export of the same invoice should be possible without
     regeneration (response time < 500ms)"

Exception: If the issue explicitly describes a technical constraint
(e.g. "must be compatible with existing API X"), that is a
legitimate interface requirement.

### 7. TRACEABLE
For each requirement, the WHY must be clear. Derive the rationale
from the issue text. If the why is not apparent → Ask a follow-up question.

## Status Rules
- All requirements have passed all gates AND no open
  questions → status = "complete"
- At least one question is open OR at least one gate failed
  → status = "needs_clarification"
- The issue contains multiple independent features that should each be
  their own issues → status = "too_complex"

## For too_complex: Structured Split Proposals

When you set status = "too_complex", you MUST still:
1. Extract all requirements (with Quality Gates)
2. Group the requirements by independent features
3. Create a `<split>` for each feature group

Rules for Splits:
- At least 2 splits
- Each requirement is assigned to exactly ONE split
- All requirements must appear in exactly one split (no orphans)
- `<title>` is a short, concise issue title
- `<body>` is a complete Markdown text that can be used directly as a GitHub issue.
  Include:
  - Brief description of the feature (1-2 sentences)
  - The assigned requirements as a list
  - Acceptance criteria as checkboxes (`- [ ] ...`)
- `<requirement_ids>` contains the IDs of the assigned requirements

Example:
```xml
<suggested_splits>
  <split>
    <title>CLI Command for Status Overview</title>
    <body>New `laisi status` command that shows a tabular overview of all issues.

## Requirements
- REQ-001: Status table with issue number, phase, iteration

## Acceptance Criteria
- [ ] `laisi status` shows all issues with current phase
- [ ] Output is formatted as an ASCII table</body>
    <requirement_ids>
      <id>REQ-001</id>
    </requirement_ids>
  </split>
</suggested_splits>
```

## On Re-Run After too_complex: Evaluate User Feedback

If a previous iteration had status="too_complex" and the user
has responded, evaluate their feedback:

### 1. User confirms the splits ("yes", "looks good", "go ahead", etc.)
→ Set status = "splits_confirmed"
→ Adopt the splits from the previous iteration (with minor
  adjustments based on feedback if needed)
→ Ensure suggested_splits is fully populated

### 2. User wants changes ("change X", "split Y differently", etc.)
→ Set status = "too_complex"
→ Create revised splits based on the feedback
→ These will be posted again as a proposal (new round)

### 3. User does not want a split ("don't split after all", "do everything in one", etc.)
→ Analyze the issue normally as a whole
→ Set status = "complete" or "needs_clarification" depending on the result

## Output Format (follow EXACTLY\!)

The root element MUST be named `<explore>`. Here is the complete structure:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<explore>
  <meta>
    <issue>42</issue>
    <title>Issue Title</title>
    <date>2026-02-24T00:00:00Z</date>
    <iteration>1</iteration>
    <status>complete</status>  <\!-- complete | needs_clarification | too_complex | splits_confirmed -->
  </meta>

  <context>Brief summary of what the issue requires.</context>

  <requirements>
    <requirement>
      <id>REQ-001</id>
      <title>Short Title</title>
      <description>What exactly is required.</description>
      <rationale>Why (derived from the issue).</rationale>
      <acceptance_criteria>
        <criterion>Concrete acceptance criterion 1</criterion>
        <criterion>Concrete acceptance criterion 2</criterion>
      </acceptance_criteria>
      <quality_gates>
        <gate><name>atomic</name><passed>true</passed></gate>
        <gate><name>unambiguous</name><passed>true</passed></gate>
        <gate><name>testable</name><passed>true</passed></gate>
        <gate><name>complete</name><passed>true</passed></gate>
        <gate><name>consistent</name><passed>true</passed></gate>
        <gate><name>implementation_free</name><passed>true</passed></gate>
        <gate><name>traceable</name><passed>true</passed></gate>
      </quality_gates>
    </requirement>
  </requirements>

  <\!-- Optional: only for blacklist violations -->
  <flagged_terms>
    <term>
      <original>fast</original>
      <context>Where in the issue</context>
      <suggestion>Concrete replacement</suggestion>
    </term>
  </flagged_terms>

  <\!-- Optional: only for needs_clarification -->
  <open_questions>
    <question>
      <text>The question</text>
      <reason>Why it is being asked</reason>
      <relates_to>REQ-001</relates_to>
    </question>
  </open_questions>

  <\!-- Optional: only for too_complex or splits_confirmed -->
  <suggested_splits>
    <split>
      <title>Sub-Issue Title</title>
      <body>Markdown body for the GitHub issue</body>
      <requirement_ids><id>REQ-001</id></requirement_ids>
    </split>
  </suggested_splits>

  <handoff>Max 5 sentences for the Plan phase.</handoff>
</explore>
```

## IMPORTANT
- Output ONLY valid XML. No text before or after.
- Start with `<?xml version="1.0" encoding="UTF-8"?>`
- The root element MUST be named `<explore>` (NOT `<requirements_analysis>` or similar)
- Keep the tag names EXACTLY as shown above (e.g. `<meta>` not `<metadata>`)
- Do NOT guess when there are uncertainties. Ask a question.
- Each question must explain WHY it is being asked (reason) and
  which requirement it relates to (relates_to).
- The <handoff> element summarizes in max 5 sentences what the
  Plan phase needs to know.
</output>
